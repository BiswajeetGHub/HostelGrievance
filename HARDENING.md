# HARDENING.md — HostelGrievance Security Improvements

## Summary

11 security findings were identified across authentication, authorisation, file handling,
session management, and HTTP configuration. All critical and high severity findings have
been remediated. Medium findings are documented with residual risk.

---

## Findings

| # | Finding | Risk | Change | Verification | Residual Risk |
|---|---------|------|--------|--------------|---------------|
| 1 | **IDOR on grievance read** — `GET /grievances/:id` and `GET /grievances/:id/comments` called `requireUser()` but never `assertCanViewGrievance()`. Any student could read any other student's grievance by guessing the ID. | Critical | Called `assertCanViewGrievance(user, row)` immediately after `requireGrievance()` in both routes in `grievances.ts`. | Logged in as two separate student accounts. Attempted to fetch the other student's grievance ID. Received 403 Forbidden. | None — server enforces ownership on every read. |
| 2 | **Session not destroyed on logout** — `POST /logout` only called `clearSessionCookie()`. The session row remained in the database. A stolen token stayed valid after logout. | Critical | Added `destroySession(db, token)` call before `clearSessionCookie()` in `auth.ts`. Token is read from cookie before clearing. | After logout, replayed the session token in a manual API request. Received 401 Unauthenticated. | None for server-side. Client must also clear local state. |
| 3 | **Session expiry not enforced** — `expires_at` was stored in the sessions table but `readSessionUser()` never checked it. Sessions never actually expired. | High | Added expiry check in `readSessionUser()`. If `expires_at` is in the past, session row is deleted and `undefined` returned. | Set a session with a past expiry directly in the DB. Attempted API call. Received 401. | None — expiry now enforced on every request. |
| 4 | **Weak password hashing (SHA-256)** — Passwords stored as unsalted SHA-256 hashes. Trivially crackable with rainbow tables. Not suitable for password storage. | Critical | Replaced `hashPassword()` and `verifyPassword()` in `passwords.ts` with bcryptjs using 12 salt rounds. | Created new user, verified hash in DB starts with `$2b$` (bcrypt format). Login verified working. | Existing seed data passwords use old format and will fail until DB is reseeded. |
| 5 | **Path traversal on file write** — `newStoredName()` accepted `originalName` parameter and used it as the stored filename. `writeStoredFile()` had no path traversal check. An attacker could write to arbitrary paths. | Critical | Removed `originalName` parameter from `newStoredName()`. Stored filename is always `randomBytes(16).toString('hex') + extension`. | Uploaded file named `../../server/app.ts`. Confirmed file stored as random hex name in uploads directory only. | None — original filename never used for storage. |
| 6 | **Session cookie missing httpOnly and SameSite** — Cookie accessible to JavaScript (XSS risk) and sent on cross-origin requests (CSRF risk). | High | Added `httpOnly: true` and `sameSite: 'Lax'` to `setCookie()` call in `session.ts`. | Inspected Set-Cookie header in browser DevTools. Confirmed both flags present. | `Secure` flag not set in app code — relies on HTTPS at infrastructure layer. |
| 7 | **Files served with Content-Disposition: inline** — Uploaded files rendered directly in browser. A polyglot or mislabeled file could execute in browser context. | High | Changed `Content-Disposition` from `inline` to `attachment` in `attachments.ts`. | Clicked attachment link. Browser prompted file download instead of rendering in tab. | Relies on browser respecting `attachment` disposition. |
| 8 | **CORS wildcard with credentials** — `origin: (origin) => origin ?? '*'` with `credentials: true` allowed any website to make authenticated requests on behalf of logged-in users. | High | Restricted `origin` to `'http://localhost:5173'` in `app.ts`. | Sent credentialed request from a different origin. Request rejected with CORS error. | Production origin must be updated before deployment. |
| 9 | **No security headers** — Missing `X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy` headers. Browsers could sniff content types or render app in iframes. | Medium | Added middleware in `app.ts` setting `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`. | Checked response headers in browser DevTools Network tab. All three headers confirmed present. | No Content-Security-Policy added — would require frontend changes. |
| 10 | **No login rate limiting** — Unlimited POST `/api/login` requests allowed. Attacker could brute force any account. | High | Added in-memory rate limiter in `auth.ts`. Maximum 5 attempts per IP per minute. Returns 429 on breach. | Sent 6 rapid login requests from same IP. 6th request returned 429 Too Many Requests. | In-memory store resets on server restart. Distributed attacks from multiple IPs not blocked. |
| 11 | **No security event logging** — Failed authentication and authorisation events produced no server-side log entries. Impossible to detect or investigate attacks. | Medium | Added logging middleware in `app.ts`. All 401, 403, and 429 responses logged with timestamp, method, path, and IP. | Triggered a 403 by accessing another student's grievance. Confirmed log entry appeared in server console. | Logs go to stdout only. Production deployment should pipe to a persistent log store. |
